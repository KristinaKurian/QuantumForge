# Задание 1. Исследование моделей и инфраструктуры

## 1. Вводные данные и требования

QuantumForge Software планирует создать внутреннего RAG-бота для поиска информации в корпоративной базе знаний.

Объём исходных данных:

* около 18 000 Markdown/MDX-файлов;
* около 3 000 страниц Confluence;
* около 250 PDF-документов;
* прирост — около 400 страниц в месяц.

Основные пользователи системы — разработчики, техническая поддержка, менеджеры, аналитики и новые сотрудники.

При выборе архитектуры необходимо учитывать не только качество ответов, но также
* стоимость эксплуатации
* скорость работы
* сложность поддержки
* возможность масштабирования
* требования к конфиденциальности корпоративной информации.

Отдельно важно учитывать, что часть документации может содержать внутренние архитектурные решения, сведения об инфраструктуре, конфигурациях клиентов и другие данные, которые нежелательно без дополнительного контроля передавать внешнему LLM-провайдеру.

# 2. Сравнение LLM-моделей

Для исследования рассмотрены три основных варианта:

1. локальная open-source LLM из Hugging Face, например Qwen3-8B;
2. облачные модели OpenAI;
3. YandexGPT.

В качестве примера локальной модели можно использовать `Qwen/Qwen3-8B`. Модель распространяется под Apache 2.0 и может запускаться локально через Transformers, vLLM, SGLang или Docker.

| Критерий                               | Локальная Hugging Face LLM                                                               | OpenAI                                                               | YandexGPT                                              |
| -------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------ |
| Качество ответа                        | Хорошее для RAG при правильно найденном контексте, но сильно зависит от выбранной модели | Высокое качество генерации и reasoning, особенно у моделей Terra/Sol | Хорошее качество, особенно для русскоязычных сценариев |
| Английская техническая документация    | Хорошо                                                                                   | Очень хорошо                                                         | Поддерживается, но русский язык является приоритетным  |
| Скорость                               | Зависит от GPU и размера модели                                                          | Высокая, инфраструктура провайдера                                   | Высокая, инфраструктура провайдера                     |
| Стоимость одного запроса               | Нет оплаты за токены                                                                     | Оплата за токены                                                     | Оплата за токены                                       |
| Постоянные затраты                     | GPU + сервер + эксплуатация                                                              | Практически отсутствуют                                              | Практически отсутствуют                                |
| Развёртывание                          | Наиболее сложное                                                                         | Простое API                                                          | Простое API                                            |
| Масштабирование                        | Нужно организовывать самостоятельно                                                      | Выполняет провайдер                                                  | Выполняет провайдер                                    |
| Работа с конфиденциальными документами | Максимальный контроль                                                                    | Необходима корпоративная политика обработки данных                   | Необходима корпоративная политика обработки данных     |
| Vendor lock-in                         | Низкий                                                                                   | Средний/высокий                                                      | Средний/высокий                                        |

### Локальная Hugging Face LLM

Главным преимуществом локальной модели является контроль над данными. Запрос пользователя и найденные фрагменты корпоративной документации могут обрабатываться внутри инфраструктуры QuantumForge.

Это особенно важно для документов, содержащих закрытую архитектурную информацию или сведения клиентов/персональные данные.

Недостаток — необходимость собственной inference-инфраструктуры:

`RAG API → vLLM/TGI → GPU → local LLM`

Необходимо самостоятельно контролировать GPU, обновление моделей, memory usage, batching, autoscaling и мониторинг.

Для RAG-системы модель класса 7–14B может быть достаточной, поскольку фактические знания поступают из retrieval-контекста, а LLM в основном формирует ответ на основе найденных документов.

### OpenAI

Преимуществами OpenAI являются простота интеграции, отсутствие собственной GPU-инфраструктуры и высокое качество генерации.

Для корпоративного RAG нет необходимости отправлять в модель всю базу знаний. В API попадают вопрос пользователя и несколько найденных retrieval-фрагментов.

Дополнительным преимуществом для европейской компании является наличие у OpenAI вариантов data residency в Европе для подходящих API-клиентов. OpenAI также указывает, что данные API-клиентов по умолчанию не используются для обучения моделей.

При этом использование внешней модели всё равно должно быть согласовано с внутренней классификацией данных компании. Наличие технических механизмов защиты не означает, что любой корпоративный документ автоматически разрешено отправлять во внешний сервис.

### YandexGPT

YandexGPT также позволяет отказаться от поддержки собственной GPU-инфраструктуры.

Для QuantumForge недостатком является то, что компания уже использует AWS, поэтому появляется дополнительный облачный провайдер и дополнительная интеграция.

### Вывод по LLM

Для MVP наиболее рациональным облачным вариантом является модель уровня GPT-5.6 Terra или, если требуется сильнее оптимизировать стоимость, GPT-5.6 Luna.

Для конфиденциальных документов рекомендуется предусмотреть возможность использования локальной модели, например Qwen3-8B/14B.

Таким образом, целевой вариант может поддерживать два режима:

```text
обычные документы
       ↓
OpenAI API
       ↓
ответ

конфиденциальные документы
       ↓
Local LLM
       ↓
ответ
```

# 3. Сравнение моделей эмбеддингов

Рассматриваются:

* Sentence-Transformers;
* OpenAI Embeddings.

Sentence-Transformers поддерживает отдельное кодирование поискового запроса и документа через `encode_query()` и `encode_document()`, что особенно подходит для RAG, где короткий вопрос пользователя сопоставляется с более длинными фрагментами документации. Документация также указывает, что semantic search хорошо работает для корпусов значительно крупнее рассматриваемой базы QuantumForge.

В качестве первой локальной модели тестируем:

```text
sentence-transformers/multi-qa-mpnet-base-cos-v1
```

Она предназначена именно для semantic search.

У OpenAI доступны `text-embedding-3-small` и `text-embedding-3-large`. Стоимость составляет соответственно $0.02 и $0.13 за 1 млн входных токенов. `text-embedding-3-large` позиционируется как более сильная модель для английских и неанглийских задач.

| Критерий             | Sentence-Transformers              | OpenAI Embeddings                        |
| -------------------- | ---------------------------------- | ---------------------------------------- |
| Где выполняется      | Локально                           | API OpenAI                               |
| Стоимость API        | Нет                                | За количество токенов                    |
| Требования к серверу | CPU или GPU                        | Минимальные                              |
| Скорость индексации  | Высокая на GPU, приемлемая на CPU  | Высокая, но зависит от сети и API limits |
| Конфиденциальность   | Данные не покидают инфраструктуру  | Текст отправляется API-провайдеру        |
| Качество             | Сильно зависит от выбранной модели | Высокое и стабильное                     |
| Настройка            | Можно менять и дообучать модели    | Модель управляется провайдером           |
| Vendor lock-in       | Низкий                             | Есть                                     |

### Стоимость создания индекса

Стоимость облачных embeddings в данном кейсе невелика.

Например, если после извлечения и chunking исходная база содержит условно 20 млн токенов:

```text
text-embedding-3-small:

20 × $0.02 = $0.40
```

Для `text-embedding-3-large`:

```text
20 × $0.13 = $2.60
```

Это только пример расчёта — точное количество токенов необходимо определить после загрузки и chunking документов.

Таким образом, сама стоимость первичного создания embeddings практически не влияет на бюджет проекта. Гораздо важнее вопросы конфиденциальности, качества retrieval и зависимости от внешнего API.

### Вывод по embeddings

Для QuantumForge я бы начала с локального Sentence-Transformers.

Причины:

* embeddings корпоративных документов создаются внутри инфраструктуры;
* отсутствует стоимость повторной переиндексации;
* отсутствует зависимость от внешнего API;
* размер базы достаточно небольшой для локальной обработки;
* embedding-модель впоследствии можно заменить, не меняя остальную архитектуру.

При этом правильность выбора необходимо подтвердить экспериментом.

Следует подготовить набор примерно из 50–100 реальных вопросов сотрудников и сравнить минимум две embedding-модели по метрикам:

```text
Recall@K
MRR
Hit Rate@K
nDCG@K
```

Выбирать embedding-модель только по публичным benchmark недостаточно — необходимо проверить retrieval именно на документации QuantumForge.

# 4. Сравнение FAISS и ChromaDB

## FAISS

FAISS — библиотека Meta для эффективного similarity search и кластеризации плотных векторов. Она написана на C++ и имеет Python API; часть алгоритмов может использовать GPU.

Важно отметить, что FAISS технически является не полноценной базой данных, а библиотекой и векторным индексом.

Преимущества:

* высокая скорость;
* небольшой overhead;
* простое использование из Python;
* поддержка различных ANN-индексов;
* возможность работы полностью локально;
* отсутствие отдельного серверного компонента;
* отсутствие стоимости лицензии.

Недостатки:

* нет полноценной системы управления metadata;
* необходимо самостоятельно сохранять индекс;
* обновления и удаление документов сложнее, чем в полноценной БД;
* нет встроенной распределённой архитектуры;
* масштабирование и репликацию необходимо делать самостоятельно.

## ChromaDB

Chroma представляет собой более полноценную систему хранения и retrieval. Она умеет хранить embeddings, документы и metadata, выполнять metadata filtering, dense/sparse/hybrid search и работать как локально, так и в client-server архитектуре. Chroma распространяется под Apache 2.0.

Chroma поддерживает несколько режимов работы: embedded/local, single-node и distributed. В документации single-node рассматривается как вариант для небольших и средних workload примерно до миллионов записей, что значительно превышает ожидаемый размер индекса QuantumForge.

| Критерий                      | FAISS                                    | ChromaDB                             |
| ----------------------------- | ---------------------------------------- | ------------------------------------ |
| Тип                           | Библиотека/index                         | Vector database / retrieval system   |
| Vector search                 | Да                                       | Да                                   |
| Metadata                      | Нужно организовывать отдельно            | Встроено                             |
| Metadata filtering            | Ограниченно/вручную                      | Есть                                 |
| Persistence                   | Необходимо контролировать самостоятельно | Встроено                             |
| Работа как отдельный сервис   | Нет необходимости                        | Есть                                 |
| Raw search overhead           | Минимальный                              | Выше из-за дополнительного слоя БД   |
| Внедрение MVP                 | Очень простое                            | Немного сложнее                      |
| Масштабирование               | Реализуется приложением                  | Есть отдельные варианты deployment   |
| Стоимость лицензии            | Бесплатно                                | Бесплатно для OSS                    |
| Инфраструктурная стоимость    | Минимальная                              | Потребуется отдельный процесс/сервис |
| Подходит для текущего проекта | Да                                       | Да                                   |

### Выбор для проектной работы

Для текущего RAG-бота я выбираю **FAISS**.

Причины выбора:

1. Объём данных относительно небольшой.
2. Для MVP не требуется распределённая vector database.
3. FAISS имеет минимальную инфраструктурную сложность.
4. Он хорошо интегрируется с LangChain.
5. Не нужен отдельный database server.
6. В проектном задании FAISS уже указан как рекомендуемый минимальный вариант.
7. Его достаточно для демонстрации полного RAG pipeline:

```text
Documents
    ↓
Chunking
    ↓
Embeddings
    ↓
FAISS
    ↓
Similarity Search
    ↓
Top-K chunks
    ↓
LLM
    ↓
Answer
```

ChromaDB имеет смысл рассматривать как следующий этап развития системы, когда появится необходимость в более развитой работе с metadata, большом количестве коллекций, независимом сервисе retrieval и более сложном жизненном цикле данных.

# 5. Рекомендуемая серверная конфигурация

Требования к серверу существенно зависят от того, где запускается LLM.

## Вариант с облачной LLM

Если генерация выполняется OpenAI или YandexGPT:

| Ресурс          | Рекомендуемая конфигурация |
| --------------- | -------------------------- |
| CPU             | 4–8 vCPU                   |
| RAM             | 16–32 GB                   |
| GPU             | Не требуется               |
| SSD             | 100 GB+                    |
| ОС              | Linux                      |
| Контейнеризация | Docker / Kubernetes        |

Этого достаточно для API бота, LangChain, Sentence-Transformers, FAISS и обработки документов.

Для первичной массовой индексации локальной embedding-моделью можно временно использовать GPU.

## Вариант с локальной LLM

Для Qwen3-8B и аналогичной модели:

| Ресурс          | Рекомендуемая конфигурация |
| --------------- | -------------------------- |
| CPU             | 16 vCPU                    |
| RAM             | 64 GB                      |
| GPU             | NVIDIA GPU с 24 GB VRAM    |
| SSD             | 200 GB NVMe                |
| ОС              | Linux                      |
| LLM server      | vLLM / аналог              |
| Контейнеризация | Docker / Kubernetes        |

24 GB VRAM даёт разумный запас для quantized 7–8B модели и inference. Для модели порядка 14B, большого контекста или нескольких одновременных запросов желательно рассматривать GPU с 48 GB VRAM.

# 6. Варианты архитектуры

## Вариант A — полностью облачный OpenAI

```text
OpenAI GPT-5.6 Terra
+
OpenAI text-embedding-3-small
+
FAISS
```

Преимущества:

* минимальное время разработки;
* практически не требуется ML-инфраструктура;
* высокое качество;
* простое масштабирование.

Недостатки:

* данные передаются внешнему провайдеру;
* оплата за каждый запрос;
* зависимость от API;
* необходимо отдельно проверить корпоративные требования по обработке конфиденциальной информации.

Подходит для быстрого MVP.

---

## Вариант B — полностью локальный

```text
Qwen3-8B
+
Sentence-Transformers
+
FAISS
```

Преимущества:

* корпоративные данные не покидают инфраструктуру;
* нет оплаты за токены;
* минимальный vendor lock-in;
* можно работать даже без доступа во внешний интернет.

Недостатки:

* необходим GPU;
* сложнее эксплуатация;
* необходимо самостоятельно обеспечивать масштабирование;
* качество генерации необходимо тщательно проверить.

Подходит для наиболее чувствительных данных.

---

## Вариант C — Yandex Cloud

```text
YandexGPT Pro / Lite
+
Cloud embeddings
+
FAISS или ChromaDB
```

Преимущества:

* нет необходимости содержать GPU;
* простое API;
* хорошая поддержка русского языка.

Недостатки:

* появляется второй cloud provider рядом с существующим AWS;
* необходимо отдельно проверить качество на англоязычной технической документации;
* появляется дополнительная внешняя зависимость.

Для QuantumForge преимущества этого варианта не настолько очевидны, поскольку текущая инфраструктура компании уже построена вокруг AWS, а значительная часть технической информации англоязычная.

---

## Вариант D — гибридная архитектура

```text
                     ┌─ non-sensitive ─→ OpenAI
Question → Retrieval ┤
                     └─ sensitive ─────→ Local LLM

             ↑
Sentence-Transformers
             ↑
           FAISS
```

Документы предварительно получают classification/metadata:

```text
PUBLIC
INTERNAL
CONFIDENTIAL
RESTRICTED
```

Для разрешённых документов можно использовать облачную LLM.

Для `CONFIDENTIAL` и `RESTRICTED` запрос маршрутизируется в локальную модель.

Такой подход позволяет совместить качество облачной LLM с возможностью полностью локальной обработки чувствительной информации.

# 7. Итоговая рекомендация

Для учебного MVP предлагается следующий стек:

```text
Python 3.11
FastAPI
LangChain
Sentence-Transformers
FAISS
OpenAI API / локальная LLM
Docker
```

**Векторное хранилище — FAISS.**

Основная причина выбора FAISS — текущий объём корпоративной базы не требует полноценной распределённой vector database, поэтому введение отдельного сервиса ChromaDB на этапе MVP увеличит сложность решения без существенной бизнес-пользы.

Для embeddings рекомендуется начать с Sentence-Transformers и затем сравнить несколько моделей на собственном наборе вопросов.

Для LLM на этапе MVP наиболее простой вариант — облачная модель уровня GPT-5.6 Terra/Luna. Для целевой корпоративной системы рекомендуется предусмотреть локальную LLM для документов, которые по политике информационной безопасности нельзя передавать внешнему провайдеру.

Целевая архитектура:

```text
Sources
GitHub / Confluence / PDF
          ↓
     Document Loader
          ↓
 Cleaning + Deduplication
          ↓
       Chunking
          ↓
Sentence-Transformers
          ↓
        FAISS
          ↓
 Similarity Search
          ↓
     relevance check
       ↙          ↘
low score       good score
   ↓                ↓
"Я не знаю"     Top-K context
                    ↓
             Security router
               ↙        ↘
           Local LLM    Cloud LLM
               ↘        ↙
                 Answer
```

Такое решение закрывает основные требования QuantumForge:

* сокращает время поиска;
* позволяет отвечать только на основании корпоративной базы знаний;
* позволяет реализовать честный ответ «Я не знаю», если релевантных документов нет;
* не требует сложной vector database на этапе MVP;
* позволяет постепенно масштабировать систему;
* предусматривает работу с конфиденциальными данными;
* не создаёт сильной зависимости между retrieval-слоем и конкретной LLM.

В дальнейшем FAISS можно заменить на ChromaDB или другое специализированное векторное хранилище без изменения общей логики RAG pipeline.
